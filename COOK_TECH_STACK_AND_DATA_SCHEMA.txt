Reviewed: 4 November 2026
Local source baseline: 6e87efb ("some lang."). Claude is editing translations separately.
This describes the checked-out implementation, not verified live infrastructure.

STACK AND ARCHITECTURE
- Frontend: HTML5, CSS and vanilla JavaScript. No React, frontend framework,
  application server, ORM or npm-based runtime build is present.
- Six static documents: index.html (welcome), recipes.html (catalog),
  recipe.html?id=ID, kitchen.html, cook.html?id=ID and history.html.
  Navigation loads a new document. Shared dialogs and page markup come from
  tools/page-template.html; tools/build-pages.cjs produces the six HTML files.
  The committed HTML can be served directly; recipe changes need no new HTML file.
- Browser architecture: shared scripts expose small window APIs rather than ES
  modules. app.js handles UI/state; cook-core.js handles arithmetic and dependency
  scheduling; recipes.js converts recipe definitions into usable ingredients/steps;
  page-session.js carries tab state; fridge.js handles ingredient matching/speech;
  account.js handles Auth and database calls. Translation packs are lazy-loaded.
- Backend: managed Supabase Auth plus PostgreSQL, exposed through its generated
  REST API (PostgREST) and SQL RPC functions. The browser talks directly to these
  APIs using the bundled Supabase JavaScript client, version 2.118.0.
- Database code: SQL and PL/pgSQL migrations, row-level security (RLS), constraints,
  indexes, security-definer RPC functions and timestamp triggers.
  RLS is the server-side ownership boundary; browser UI checks are not permissions.
- Infrastructure: account configuration targets GitHub Pages under /cook/ and a
  Supabase project. HTTPS, deployment source, applied migrations, database version,
  region/plan, SMTP provider and production limits were not inspected live.
- Other services: api.country.is supplies an IP-based country hint for speech
  language. Web Speech API recognition may use the browser vendor's remote service.
  Main app fonts, icons and photos are local assets. The tracked voicetest.html
  prototype additionally loads Google Fonts and has different storage/security rules.
- Development: Node.js runs page generation and tests; Python/Pillow helpers convert
  images. These are local tools, not a Node/Python production backend. No object
  storage/upload service, Edge Function or native mobile app is implemented here.

DATA FLOW
Google Sheets-authoring -> copied local recipe/translation data -> static site.
Recipe choices -> build(choices) -> ingredient quantities + dependency-based steps.
Guest navigation state -> path-scoped sessionStorage in the current tab.
Authenticated requests -> Supabase Auth -> RLS-protected PostgreSQL records.
Public comments/rating aggregates -> narrowly projected SQL RPC responses.
There is no live Sheets fetch in the visitor's recipe-loading path.

RECIPE AND BROWSER DATA (logical model, not database tables)
Recipe [id]
  name, image, category, cuisine[], optional unit/serving limits, metadata;
  options[] {id, question, choices[] {id, label, isDefault}};
  build(choices) -> {servings, ingredients[], steps[]}.
  Most definitions originate as pipe-delimited O/I/S rows in recipes-sheet.js;
  Carbonara has a separate hand-written builder. Some metadata is maintained in code.
Choices [recipe id]
  adults, kids, derived servings, guidance mode, and opt_* choice IDs.
Built ingredient [id within recipe]
  name, shared ingredient key, displayed amount, grams, note, optional noImage.
Built step [id within recipe]
  thread, area, title/text, duration seconds, deps[] of step IDs, tools[] of equipment
  IDs, ings[] of ingredient references/amounts, completion text and optional tips,
  overcook flag, merged parts/members for quick mode.
Dependency graph
  Explicit deps plus the preceding step in the same thread; CookCore validates and
  caches a topological graph in a WeakMap, then schedules earliest start/finish times.
Ingredient reference [image/ingredient key]
  Nutrition estimates, allergens, diet/hazard tags and category in INGREDIENT_INFO.
Equipment [equipment id]
  Display name and optional local SVG path in EQUIPMENT.
Language pack [language code]
  UI strings, ingredient names, recipe names and text translations; English UK also
  has a word map. There are 45 non-default pack files; English US is built in.
Tab session [site path, schema version 1]
  Picks, filters/search, pantry ingredient keys, favorites, layout rectangles,
  language/theme/units/map settings and an optional cooking snapshot.
  Cooking stores recipe/step IDs, choices, completed IDs, timestamps, pause/progress
  metadata and historyId. It does not store DOM nodes, functions or guest star votes.
Account preferences
  layout {areaKey: {x,y,w,h}}, layoutSaved/layoutTouched/layoutWide, textures,
  lang, theme, units and optional favorites[] of recipe IDs.
  Only these preference fields are synced; tab search/picks/pantry are separate.
Authentication storage
  Auth session tokens use sessionStorage by default. "Stay signed in" switches
  them to localStorage and retains theme/language. Keys are scoped by site path.
  No password is included in recipe snapshots or settings exports.

DATABASE (as defined by the migration files; application status is unverified)
auth.users [Supabase-managed]
  id UUID, email, encrypted password/authentication records, confirmation metadata.
  One user -> one settings row, profile and shopping list; many ratings/history/comments.
public.user_settings
  user_id UUID PK/FK -> auth.users; preferences JSONB; updated_at timestamp.
public.recipe_ratings
  (user_id UUID, recipe_id text) composite PK; stars smallint 1..5; updated_at.
public.profiles
  user_id UUID PK/FK; username text 3..30 characters; updated_at.
  A unique index enforces lower(username) uniqueness.
public.cook_history
  id bigint identity PK; user_id FK; recipe_id; cooked_at; choices JSONB;
  minutes_taken, minutes_suggested; optional stars and personal note.
  Index: (user_id, cooked_at DESC). Private to its owner.
public.recipe_comments
  id bigint identity PK; user_id FK; recipe_id; body; created_at.
  Index: (recipe_id, created_at DESC). Owners insert/delete their own comments.
public.shopping_lists
  user_id UUID PK/FK; items JSONB array; updated_at.
  Client item shape: {k, key, name, qty, unit, count, recipe, done}.
  Stored as a whole-list replacement, not one row per item.

RELATIONSHIPS AND PERMISSIONS
- All application user_id references cascade on Auth user deletion.
- All six public tables enable and force RLS. Most owner operations additionally
  require confirmed email; some owner cleanup/read policies intentionally do not.
- Recipe IDs in database rows are text checked by a pattern, not foreign keys to
  a recipe catalog. Actual recipe membership is checked only by some client methods.
- Public cook_recipe_comments(recipe) returns at most 200 comments with display
  username, optional stars and an ownership flag; not email/user_id.
- Public cook_rating_summary() returns per-recipe average and vote count.
- cook_delete_account(password) checks the current user's password hash and deletes
  that Auth user; it runs with elevated function privileges.
- Schema order: schema.sql, update-2026-10-30.sql, update-2026-11-03-ratings.sql,
  then update-2026-11-03-community.sql, then update-2026-11-06-kitchen-items.sql. Do not rerun initial setup on existing data.
